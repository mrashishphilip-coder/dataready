Product case study · October 2026

DataReady

AI agents rarely fail for lack of data. They fail because nothing checks whether a metric is fit for this question, right now. I built the check, then tested whether a well-prompted comparison agent even needs it.

The problem

"What was online GMV last week?" has a dozen ways to be wrong

Ask an internal analytics agent a metric question, such as online GMV (the total value of online sales), and it will find a definition, query the company's central data store and return a number. The number can be wrong in ways nobody sees: "revenue" meant the Sales definition, not Finance's; one region's rows never landed; yesterday's store load is still running; a quality check failed earlier in the data pipeline; the person asking isn't allowed to see the figure.

An analyst carries this context in their head. An agent doesn't, and it answers confidently, at scale, with no one checking. The tools to catch each problem exist (tools that define metrics, tools that monitor data health, data catalogues), but they sit in different places and nothing combines them for one specific request at the moment of answering.

The bet

Interpretation belongs to the model. The decision belongs to code.

A model is good at turning "online GMV for the last 7 days" into a structured request. It is not a reliable judge of whether 27 of 28 expected rows is acceptable. So the model reads the question, fixed rules decide, and the person asking settles anything ambiguous.

What would prove me wrong: the comparison agent, with the same model and tools doing as well as the check; or the check refusing questions that had a good answer. A check that refuses too often gets switched off.

The experiment

Same model, same tools. One difference.

I wrote 41 questions against fictional retail data with seven planted problems, and labelled the right response to each: answer, ask, or decline. Two agents ran on the same AI model with the same metric catalogue, synonyms and calendar conventions. The comparison agent had a tool to query the data, a tool to check data health, and instructions to decline unreliable answers. The other agent's only data tool was DataReady. Each ran all 41 questions three times.

Results

With the check, no wrong numbers. Without it, the same wrong number every run.

What I found

The comparison agent saw the warning and answered anyway

On "Online GMV for the last 7 days", the comparison agent checked data health and was warned that one region's data for one day was missing. Its own query found 27 of the 28 daily records it expected. In one run it even mentioned the gap in its answer. Then it reported ₹44,75,299, about 3.3% short, in all three runs. A gap that small goes unnoticed in a meeting.

A prompt is advice. A gate is policy.

Safer and cheaper

The agent with DataReady made one tool call instead of two or three, used about 23% less AI processing, and gave the same answer every run. The safe path became the cheap one.

The comparison agent was good

39–40 of 41 is a strong result. The problem is narrower than "agents are reckless": a well-instrumented signal gets seen and ignored, and the miss repeats.

What I got wrong

The comparison agent caught a flaw in my own product

My check refused answers it shouldn't have

In the first run, the comparison agent answered two questions DataReady had refused: store orders and average order value for a week when one region's returns data failed a quality check. Its reasoning: neither metric uses returns. It was right. I made quality checks apply only to metrics that use the affected data, corrected both labels, and re-ran everything. The first results are kept, not deleted.

A check only judges the request it's given

With keyword rules instead of a model, DataReady scored 37 of 41: it never gave a number it should have refused, but it gave four wrong numbers. Each was a date range read as a single day. The data for that day was clean, so every check passed on the wrong scope. The model interpreter fixed all four, and every answer now shows what was understood.

I also made the comparison agent fairer after run 1. It hadn't been given the metric synonyms or calendar conventions the interpreter had, and it scored 34 of 41 with that handicap. Every number on this page is from the fair version.

What I'd do next

Ship it as a feature, then test it with real metric owners

  1. Build it into the tools that already define metrics and catalogue data, where definitions, quality results and access rules already live. A standalone product would duplicate them.
  2. Replay 20 real questions from an analytics team's channel, labelled by the metric owners, and count wrong numbers, needless refusals and whether people trust the "what was understood" panel.
  3. Track one number in production: answers later corrected by a human. If the check doesn't move it, it isn't earning its place.

The code, the 41 labelled questions and every recorded run are on GitHub, so each number on this page can be checked.

Limits: synthetic data, 41 questions, one model, my own labels. Enough to show the pattern, not to estimate a production error rate. Independent labellers come next.
